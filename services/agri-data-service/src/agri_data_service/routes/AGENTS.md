# API route boundary

`local_publication.py` is the only phase-one path from a workstation-produced artifact into the operational database. The receiver is fail-closed unless its explicit enable switch, strong bearer token, and configured audit actor are all present. It enforces encoded request, output-count, per-file, and aggregate byte limits before database writes and verifies the frozen run plan, release-set manifest checksum, run-level validation, output descriptor, artifact-bound validation report, byte length, and SHA-256 checksum. Rejected transactional paths raise an internal abort so staged definitions, runs, and artifacts roll back together.

Staging freezes product and scope alongside the immutable manifest; commit accepts neither target nor caller identity and derives both target and audit actor from server-held state. Staging and per-output upload are idempotent; content-addressed artifacts use an atomic PostgreSQL upsert. Commit locks the target publication pointer and run, then rechecks the database-immutable release state and checksum with an ordinary read. It succeeds only when the exact declared output set exists and the run remains publishable. Each pointer revision receives a distinct outbox event. The resulting pointer is marked `artifact_only`; browser-facing APIs and Martin views must ignore it until a future typed loader promotes the data.

Return stable error codes without reflecting credentials, payload bytes, private paths, or validation internals. Keep public environmental read routes separate from this writer-only boundary.

The strategy read surface exposes only `approved` records, whose database constraint requires review and evidence metadata. Location and species routes stay unmounted until those records have explicit tenancy/publication governance; returning fake empty collections or exposing precise ungoverned points is not an acceptable placeholder.

`forecasts.py` is a read-only metric-forecast surface over `agri.v_forecast_series_serving`; it never reads staging tables or produces strategy recommendations. Every request is scoped to one series key and a bounded page. Native/output support and checksum lineage stay attached to each point. Spatial output is opt-in: centroids are rounded WGS84 points, while polygon GeoJSON has a smaller page cap plus nested stored-size, vertex, and encoded-byte guards. The candidate page is materialized so expensive serialization occurs once and only after cheaper guards pass; an omitted oversized polygon is signaled explicitly instead of being simplified into a different support claim. The serving statement itself lives in `sql/routes/forecast_serving.sql`; its three size caps are Python module constants baked into the text with `.format()` at import time, so any literal curly brace added to that file must be doubled or the module fails to import.

`historical_promotion.py` is a separate authenticated receiver for normalized historical rows. It accepts a bounded signed manifest, one canonical typed chunk at a time, then one raw source package at a time through an opaque natural-identity token; it never accepts a database dump, client-supplied surrogate IDs, or a release-set transition before closure checks pass. Keep the target database private; only this narrow HTTPS receiver is intended to be reachable from the local promoter.

**`_ChunkIndex` exists because chunk import was three SELECTs per record inside one open transaction on a request handler.** An 8 MB chunk is on the order of 10⁴ observation records, and each one re-resolved its source release, re-resolved its spatial cell, and probed for its own existing row — tens of thousands of serial round trips holding one pooled connection and one transaction open for the whole PUT. `_build_chunk_index` now reads the same rows in a bounded number of queries before the loop and hands the loop dictionaries. Three properties are load-bearing and must survive any edit here. **Each map is keyed by exactly the natural key the probe it replaced compared on**, so a lookup answers the identical question — the prefetch predicates are deliberately *supersets* (an instant range instead of an IN-list of every instant; all children of the chunk's releases and cells), because an exact-key dict lookup over a superset is exactly as precise as the per-row SELECT was. **A row created during the chunk is written back into the index**, so a second record naming the same key still finds it and still raises the same `*_conflict` 409 the autoflush-then-SELECT path raised — without that, a duplicate inside one chunk would degrade to an `IntegrityError` at commit and a different error code. **Prefetching only pre-existing releases and cells is complete by construction**: a release or cell created by this chunk has no children in the database to read. Conflict codes, receipt writes, checksum comparisons and the transaction boundary are all unchanged; the only record types that still cost a round trip of their own are the ones that must reach PostGIS (`_require_valid_geometry`, `_geometry_matches`) or claim a surrogate key (`session.flush()` for a new source, release or cell). The geometry validation statement lives in `sql/routes/require_valid_geometry.sql`.

`ops.py` mounts `/ops/backfill` — a read-only operator console over the `agri.job_*` durable ledger, served by this process with no build step and no second service. It answers the questions `jobs-status` cannot: rate, ETA, stall, and failure history. Six statements back it (`sql/routes/ops_*.sql`), and the per-lane rollup is deliberately one statement with three CTEs at three grains rather than a query per lane — folding attempts or checkpoints into the work-item aggregate would multiply the state counts by the attempt count. **Throughput is windows-succeeded-in-the-trailing-window divided by that window's width, and ETA is outstanding divided by that rate; a zero rate renders as an em dash and never as infinity or as a fabricated date.** The activity column is labelled *last recorded activity*, not *last cron run*, and is `GREATEST` over the item, attempt and checkpoint timestamps that the runtime actually writes: a tick that claims nothing writes nothing durable, so an idle healthy lane is indistinguishable from a cron that has not fired in days, and `updated_at` cannot substitute because every runtime write is a raw statement that never triggers the ORM's `onupdate`. The page is rendered server-side with the snapshot already in it and then kept live by SSE element patches over a vendored Datastar bundle (`static/datastar.js`, served from `/ops/static/datastar.js`) — no CDN, no external font, no bundler. It reads through `receiver_writer_session`, which is the combined-local session locally and the production receiver role on Railway; if that role lacks `SELECT` on `job_work_item`, the page says so in a banner rather than returning 500. **`/ops` is not authenticated.** It exposes lane names, shard keys and redacted error summaries, and must be gated before this service is reachable from the public internet.

**The *historical walks* section exists because only two loads use the ledger at all.** The NASA POWER and Open-Meteo ERA5-Land walks are driven by reviewed plan files, enqueue no work item, and were therefore invisible in *lanes* — no state, no progress, no elapsed time. `sql/routes/ops_historical_walks.sql` reconstructs them from the one durable row each chunk does write, an `agri.source_release`, joined only to `agri.data_source` and `agri.spatial_cell` — a few thousand rows and ~150 ms on production — plus one release-grain rollup of `agri.signal_observation` that costs the statement ~2 s and buys the `rows` column. **A walk's identity is (window, lattice, parameter set), and the parameter set is load-bearing, not decoration**: three Open-Meteo walks share one window and one lattice and differ only in whether they asked for soil temperature, soil moisture or vapour-pressure deficit, so grouping without it fuses them into one meaningless row. The two producers compose `source_version` differently — Open-Meteo appends a chunk ordinal (`cells-NNNN`) and lists its cells in `query_parameters.cell_keys`, NASA writes one release per cell with the cell key as the tail and hides its parameters inside the stored `request_url` — and both shapes are unpicked in the statement rather than in Python. **Cells done is DISTINCT cells, never a sum**, because a continuation re-covers cells the walk already holds and would otherwise report 405 of 397. The denominator is `count(*)` over `agri.spatial_cell` for the one lattice the walk's own cell keys resolve to; when they resolve to none or to two, target and completion render as an em dash and no percentage is fabricated. `idle` carries the same caveat as *last recorded activity*: a walk between chunks and a walk whose scheduled task stopped firing are indistinguishable from the database, and the only evidence either way is when the last chunk landed. The lane rows answer the same elapsed-time question from `run_started_at`, which the statement had always selected and the table had never shown.

**A walk's `rows` column exists because chunks landed and cells done cannot tell a complete walk from an empty one.** A chunk publishes an `agri.source_release` whether or not the upstream returned data, so the radiation lane's pre-fix run reads 397 of 397 cells and 8 chunks under `open-meteo-era5-land-archive` with **zero** values behind it, byte-identical on the page to the fixed run's 397 of 397, 8 chunks and 580,414 values under `open-meteo-era5-archive`. The release set is immutable provenance of what was attempted and is not deleted; instead the statement sums `agri.signal_observation` at release grain, `_walk_state` tests emptiness *before* completion so such a walk reads `no_data` rather than `complete`, and the row now prints its `data_source_key` — the two walks share a label and the source key is the only thing that separates them. **The deliberately-low completion of a subset plan is unchanged and still documented as a known limitation:** the two 4-cell soil-wetness pilots sit permanently at 4 of 397 beside the 397-of-397 plan that superseded them, and a walk-family rule over overlapping cell coverage is far more machinery than the guess about intent is worth. What `rows` settles is the adjacent question — each pilot carries exactly 4 cells × 3 parameters × 1,462 days of real values, so "small on purpose" no longer reads like "complete and empty".

**The *lanes* table now cross-checks the ledger against what landed, because for the two archive walks the ledger is abandoned.** Since 2026-08-07 `durable-archive-backfill.sh` keeps its position in a local cursor file and calls the bare `ingest-backfill` verb, which enqueues nothing — so `agri.ingest.archive_walk.firms-archive` froze at 93 of 1,882 and `…streamflow-archive` at 10 of 48, both with a `last_recorded_activity_at` of 2026-08-08 03:45, while both walks kept writing hundreds of thousands of real `geo.features` rows. `sql/routes/ops_lane_landed_evidence.sql` asks the store the same question `ops_data_streams.sql` asks: when did a row last land, how many landed in the window, and which observed days are being written right now. A run that still owes work and whose ledger has recorded nothing for `_LEDGER_STALE_HOURS` (6 — several times the ~1 h a 5-day FIRMS window takes) is marked `ledger stale`; its done/complete/win-h/eta/frontier cells lose their live tone but **keep their values**, which are the ledger's real last word, and the row gains a line saying what actually landed. **"Still owes work" is `outstanding - dead_letter`, on the newest run only, and never on a settled run — three guards, because the flag is worthless the moment it is always on.** `outstanding_items` is `status NOT IN ('succeeded', 'cancelled')` and therefore counts dead letters forever, while the ledger's own finalizer (`sql/jobs/refresh_job_run_rollup.sql`) folds `dead_letter` into `failed` and closes the run at `succeeded + failed = total`; keying off `outstanding_items` alone hung a permanent red pill on every campaign that ever spent a window's retry budget. `_run_is_terminal` reads the two marks that finalizer writes — a `completed_at`, or one of the five statuses `ck_job_run_terminal_run_has_completion_time` names — and `_owed_items` covers the case it cannot see, an abandoned driver that never calls the finalizer at all and leaves a fully dead-lettered run sitting at `running`. `_current_run_ids` supplies the third: lowering a lane's floor mints a **second** run and leaves the first in the ledger forever, and because the landed-evidence line is keyed by *stream* rather than by run, a superseded run allowed to wear it would print the current run's live activity beside a campaign that stopped weeks ago. The line is worded **stream-wide** and carries its window for the same reason — several lanes may write one stream — and the day pair under the frontier carries `(last hour)` because that column really is a different, fixed window from the row count beside it. **The fix is to the display only.** Wiring the driver back into the job/work-item/attempt/checkpoint protocol is a schema and semantics change and was deliberately not attempted. The lane-to-stream map is *derived* from `ingest.validation.models.DEFAULT_STREAM_DEFINITIONS`, whose `lane_names` already come from `archive_lane_definition_name` over the registered lanes, so this page and the validity report cannot spell a lane two ways; a lane absent from that catalog gets an honest "no stream is mapped to this lane" rather than a borrowed reassurance.

**Three of the six statements scan a whole table and each is cached on its own clock** in `_QUERY_CACHE`, keyed by statement and by the rate window where that changes the answer: data loads at 300 s (~26 s, aggregates all ~46M observations and all of `geo.features`), historical walks at 60 s (~2.7 s, well inside the 15-minute band that decides `active`), lane evidence at 60 s (0.3 s once `drizzle/0022` is applied, 3.8 s before, both far short of the 6 h staleness threshold, so the cross-check never flips on cache age alone). Without them the SSE loop would re-run every scan every 5 s and each connected operator would hold a permanent scan open against production. A cached number is up to its own TTL old, not 5 s old, so anything the page describes as self-correcting on the next read corrects on that clock. The lane, failure and dead-letter statements are cheap and stay live.

**Every statement runs under a 120 s transaction-local `statement_timeout`** (`_SET_STATEMENT_TIMEOUT`, pinned as the first statement of the snapshot transaction so the rest inherit it), per `sql.md` §"Query & algorithmic excellence". It is on the route rather than on `_service_session` because that pool is shared with ingest, whose chunk imports have no business being capped by a dashboard's budget. The point is that `/ops` is unauthenticated and its scanning statements grow with the archive: without a cap, unbounded growth pins a production connection silently, and with one it lands in the page's error banner. **The lane-evidence statement is index-shaped and the index is `drizzle/0022_features_write_time_indexes.sql`** — `(layer_id, created_at)` and `(layer_id, updated_at)` on `geo.features`, which had nothing on either write-time column. Two facts are load-bearing for anyone editing that statement: `max(GREATEST(a, b))` can never use an index because `GREATEST` is computed per row, and a `FILTER` restricts the aggregate rather than the scan, so the window predicate has to sit in a `WHERE`; and the per-layer scan has to be a `CROSS JOIN LATERAL`, because joining `geo.features` to the layer CTE on `layer_id` makes the planner hash them and a hashed join key cannot become an index condition. Measured on a 2.4M-row replica carrying 0022: 0.33 s for the lateral shape against 2.1 s for the original. Measured on production *without* 0022 the new shape is **slower** (3.8 s against 2.2 s), so the migration and this code belong in the same change.

`health/` is a package, not a module, because 92% of the old 1279-line file was four SQL literals. It is now two probe statements in `sql/routes/health_*.sql` plus `contracts.py` (the extension tuple and the pinned revision the readiness contract is made of), `queries.py` (renders that tuple into a SQL row-literal with `_sql_values` and `.format()`s it into the loaded file at import), `probes.py` (the fixed probe order), and `__init__.py` (the blueprint, both handlers, and a re-export of every name this package exposes). **The probe SQL is operator-facing documentation now.** When `/ready` answers `extensions: false` the next question is always "which one, and why does it matter", and that answer belongs beside the statement that asked it — each `.sql` file carries a clause-by-clause walkthrough written for someone who does not know SQL, explaining what `has_table_privilege` checks, why `coalesce` is needed around it, and why the Alembic revision is pinned to an exact value in both directions. **Two structural rules hold the package together.** The SQL strings stay plain `str` (`text()` objects sit beside them) because `tests/test_forecasting_postgresql.py` hands them to psycopg2 and `tests/test_health_readiness.py` asserts substrings of them. And the handlers stay in `__init__.py` rather than moving to a submodule: `settings`, `published_reader_session` and `receiver_writer_session` are module globals that tests rebind with `monkeypatch.setattr` on this package, and a handler defined one level down would read its own globals, sail past the patch, and open a real connection during the unit suite — a test that silently stops testing what it names.

**Revision `20260808_0019` deleted the role half of this package**, and the deletion is the point rather than an omission to repair. `contracts.py` used to carry `FORECAST_ROLES` and four privilege matrices, `queries.py` rendered them into `health_forecast_role_contract.sql` and `health_receiver_role_boundary.sql`, and `/ready` reported `profile_tables`, `runtime_privileges` and `forecast_role_contracts`. That whole apparatus asserted an "exactly these privileges and no more" contract over four `NOLOGIN` capability roles which — verified on a head-migrated database — had **zero members, no DSN, and no `USAGE` on schema `agri`** after `20260803_0018` orphaned them. The owner retired the family; every application now connects with the single owner credential, and an "and nothing more" assertion about an owner is vacuous, so the sections making it were removed rather than softened into checks that always pass. `tests/test_health_readiness.py` asserts the retired fragments are *absent* from the statement so they cannot drift back in. See `docs/reports/migration-decision-packet-2026-08-08.md` § Resolution.

`/health` is process liveness. `/ready` is profile-specific rollout evidence, and it now reports exactly five checks: `database_profile`, `receiver_identity`, `extensions`, `migration`, `serving_surface`. The `receiver_writer` profile mounts only the two authenticated receivers and requires a server-bound receiver actor. The `published_reader` profile mounts only `forecasts.py` and does not require receiver credentials. Both profiles require the exact Alembic revision and all four extensions. `combined_local` mounts the compatibility surface but always fails readiness. Redis is not a data-service dependency in phase one: publication commits an outbox record in the same PostgreSQL transaction, and another bounded dispatcher may deliver that event later.
