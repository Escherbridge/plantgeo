# API route boundary

`local_publication.py` is the only phase-one path from a workstation-produced artifact into the operational database. The receiver is fail-closed unless its explicit enable switch, strong bearer token, and configured audit actor are all present. It enforces encoded request, output-count, per-file, and aggregate byte limits before database writes and verifies the frozen run plan, release-set manifest checksum, run-level validation, output descriptor, artifact-bound validation report, byte length, and SHA-256 checksum. Rejected transactional paths raise an internal abort so staged definitions, runs, and artifacts roll back together.

Staging freezes product and scope alongside the immutable manifest; commit accepts neither target nor caller identity and derives both target and audit actor from server-held state. Staging and per-output upload are idempotent; content-addressed artifacts use an atomic PostgreSQL upsert. Commit locks the target publication pointer and run, then rechecks the database-immutable release state and checksum with an ordinary read. It succeeds only when the exact declared output set exists and the run remains publishable. Each pointer revision receives a distinct outbox event. The resulting pointer is marked `artifact_only`; browser-facing APIs and Martin views must ignore it until a future typed loader promotes the data.

Return stable error codes without reflecting credentials, payload bytes, private paths, or validation internals. Keep public environmental read routes separate from this writer-only boundary.

The strategy read surface exposes only `approved` records, whose database constraint requires review and evidence metadata. Location and species routes stay unmounted until those records have explicit tenancy/publication governance; returning fake empty collections or exposing precise ungoverned points is not an acceptable placeholder.

`forecasts.py` is a read-only metric-forecast surface over `agri.v_forecast_series_serving`; it never reads staging tables or produces strategy recommendations. Every request is scoped to one series key and a bounded page. Native/output support and checksum lineage stay attached to each point. Spatial output is opt-in: centroids are rounded WGS84 points, while polygon GeoJSON has a smaller page cap plus nested stored-size, vertex, and encoded-byte guards. The candidate page is materialized so expensive serialization occurs once and only after cheaper guards pass; an omitted oversized polygon is signaled explicitly instead of being simplified into a different support claim.

`historical_promotion.py` is a separate authenticated receiver for normalized historical rows. It accepts a bounded signed manifest, one canonical typed chunk at a time, then one raw source package at a time through an opaque natural-identity token; it never accepts a database dump, client-supplied surrogate IDs, or a release-set transition before closure checks pass. Keep the target database private; only this narrow HTTPS receiver is intended to be reachable from the local promoter.

`/health` is process liveness. `/ready` is profile-specific rollout evidence. The `receiver_writer` profile mounts only the two authenticated receivers, requires a server-bound receiver actor, and rejects a login with published-reader membership or serving-view access. The `published_reader` profile mounts only `forecasts.py`, does not require receiver credentials, and requires the API login to be a member of reader only. Both profiles require the exact Alembic revision, all four extensions, route-touched objects, and the complete four-role relation/column/sequence/function matrix without nesting, elevation, grant options, or `PUBLIC` execution. `combined_local` mounts the compatibility surface but always fails readiness. Redis is not a data-service dependency in phase one: publication commits an outbox record in the same PostgreSQL transaction, and another bounded dispatcher may deliver that event later.
