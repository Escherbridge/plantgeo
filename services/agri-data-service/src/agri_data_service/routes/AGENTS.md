# API route boundary

`local_publication.py` is the only phase-one path from a workstation-produced artifact into the operational database. The receiver is fail-closed unless its explicit enable switch, strong bearer token, and configured audit actor are all present. It enforces encoded request, output-count, per-file, and aggregate byte limits before database writes and verifies the frozen run plan, release-set manifest checksum, run-level validation, output descriptor, artifact-bound validation report, byte length, and SHA-256 checksum. Rejected transactional paths raise an internal abort so staged definitions, runs, and artifacts roll back together.

Staging freezes product and scope alongside the immutable manifest; commit accepts neither target nor caller identity and derives both target and audit actor from server-held state. Staging and per-output upload are idempotent; content-addressed artifacts use an atomic PostgreSQL upsert. Commit locks the target publication pointer and run, then rechecks the database-immutable release state and checksum with an ordinary read. It succeeds only when the exact declared output set exists and the run remains publishable. Each pointer revision receives a distinct outbox event. The resulting pointer is marked `artifact_only`; browser-facing APIs and Martin views must ignore it until a future typed loader promotes the data.

Return stable error codes without reflecting credentials, payload bytes, private paths, or validation internals. Keep public environmental read routes separate from this writer-only boundary.

The strategy read surface exposes only `approved` records, whose database constraint requires review and evidence metadata. Location and species routes stay unmounted until those records have explicit tenancy/publication governance; returning fake empty collections or exposing precise ungoverned points is not an acceptable placeholder.

`forecasts.py` is a read-only metric-forecast surface over `agri.v_forecast_series_serving`; it never reads staging tables or produces strategy recommendations. Every request is scoped to one series key and a bounded page. Native/output support and checksum lineage stay attached to each point. Spatial output is opt-in: centroids are rounded WGS84 points, while polygon GeoJSON has a smaller page cap plus nested stored-size, vertex, and encoded-byte guards. The candidate page is materialized so expensive serialization occurs once and only after cheaper guards pass; an omitted oversized polygon is signaled explicitly instead of being simplified into a different support claim. The serving statement itself lives in `sql/routes/forecast_serving.sql`; its three size caps are Python module constants baked into the text with `.format()` at import time, so any literal curly brace added to that file must be doubled or the module fails to import.

`historical_promotion.py` is a separate authenticated receiver for normalized historical rows. It accepts a bounded signed manifest, one canonical typed chunk at a time, then one raw source package at a time through an opaque natural-identity token; it never accepts a database dump, client-supplied surrogate IDs, or a release-set transition before closure checks pass. Keep the target database private; only this narrow HTTPS receiver is intended to be reachable from the local promoter.

**`_ChunkIndex` exists because chunk import was three SELECTs per record inside one open transaction on a request handler.** An 8 MB chunk is on the order of 10⁴ observation records, and each one re-resolved its source release, re-resolved its spatial cell, and probed for its own existing row — tens of thousands of serial round trips holding one pooled connection and one transaction open for the whole PUT. `_build_chunk_index` now reads the same rows in a bounded number of queries before the loop and hands the loop dictionaries. Three properties are load-bearing and must survive any edit here. **Each map is keyed by exactly the natural key the probe it replaced compared on**, so a lookup answers the identical question — the prefetch predicates are deliberately *supersets* (an instant range instead of an IN-list of every instant; all children of the chunk's releases and cells), because an exact-key dict lookup over a superset is exactly as precise as the per-row SELECT was. **A row created during the chunk is written back into the index**, so a second record naming the same key still finds it and still raises the same `*_conflict` 409 the autoflush-then-SELECT path raised — without that, a duplicate inside one chunk would degrade to an `IntegrityError` at commit and a different error code. **Prefetching only pre-existing releases and cells is complete by construction**: a release or cell created by this chunk has no children in the database to read. Conflict codes, receipt writes, checksum comparisons and the transaction boundary are all unchanged; the only record types that still cost a round trip of their own are the ones that must reach PostGIS (`_require_valid_geometry`, `_geometry_matches`) or claim a surrogate key (`session.flush()` for a new source, release or cell). The geometry validation statement lives in `sql/routes/require_valid_geometry.sql`.

`ops.py` mounts `/ops/backfill` — a read-only operator console over the `agri.job_*` durable ledger, served by this process with no build step and no second service. It answers the questions `jobs-status` cannot: rate, ETA, stall, and failure history. Three statements back it (`sql/routes/ops_backfill_*.sql`), and the per-lane rollup is deliberately one statement with three CTEs at three grains rather than a query per lane — folding attempts or checkpoints into the work-item aggregate would multiply the state counts by the attempt count. **Throughput is windows-succeeded-in-the-trailing-window divided by that window's width, and ETA is outstanding divided by that rate; a zero rate renders as an em dash and never as infinity or as a fabricated date.** The activity column is labelled *last recorded activity*, not *last cron run*, and is `GREATEST` over the item, attempt and checkpoint timestamps that the runtime actually writes: a tick that claims nothing writes nothing durable, so an idle healthy lane is indistinguishable from a cron that has not fired in days, and `updated_at` cannot substitute because every runtime write is a raw statement that never triggers the ORM's `onupdate`. The page is rendered server-side with the snapshot already in it and then kept live by SSE element patches over a vendored Datastar bundle (`static/datastar.js`, served from `/ops/static/datastar.js`) — no CDN, no external font, no bundler. It reads through `receiver_writer_session`, which is the combined-local session locally and the production receiver role on Railway; if that role lacks `SELECT` on `job_work_item`, the page says so in a banner rather than returning 500. **`/ops` is not authenticated.** It exposes lane names, shard keys and redacted error summaries, and must be gated before this service is reachable from the public internet.

`health/` is a package, not a module, because 92% of the old 1279-line file was four SQL literals. It is now two probe statements in `sql/routes/health_*.sql` plus `contracts.py` (the extension tuple and the pinned revision the readiness contract is made of), `queries.py` (renders that tuple into a SQL row-literal with `_sql_values` and `.format()`s it into the loaded file at import), `probes.py` (the fixed probe order), and `__init__.py` (the blueprint, both handlers, and a re-export of every name this package exposes). **The probe SQL is operator-facing documentation now.** When `/ready` answers `extensions: false` the next question is always "which one, and why does it matter", and that answer belongs beside the statement that asked it — each `.sql` file carries a clause-by-clause walkthrough written for someone who does not know SQL, explaining what `has_table_privilege` checks, why `coalesce` is needed around it, and why the Alembic revision is pinned to an exact value in both directions. **Two structural rules hold the package together.** The SQL strings stay plain `str` (`text()` objects sit beside them) because `tests/test_forecasting_postgresql.py` hands them to psycopg2 and `tests/test_health_readiness.py` asserts substrings of them. And the handlers stay in `__init__.py` rather than moving to a submodule: `settings`, `published_reader_session` and `receiver_writer_session` are module globals that tests rebind with `monkeypatch.setattr` on this package, and a handler defined one level down would read its own globals, sail past the patch, and open a real connection during the unit suite — a test that silently stops testing what it names.

**Revision `20260808_0019` deleted the role half of this package**, and the deletion is the point rather than an omission to repair. `contracts.py` used to carry `FORECAST_ROLES` and four privilege matrices, `queries.py` rendered them into `health_forecast_role_contract.sql` and `health_receiver_role_boundary.sql`, and `/ready` reported `profile_tables`, `runtime_privileges` and `forecast_role_contracts`. That whole apparatus asserted an "exactly these privileges and no more" contract over four `NOLOGIN` capability roles which — verified on a head-migrated database — had **zero members, no DSN, and no `USAGE` on schema `agri`** after `20260803_0018` orphaned them. The owner retired the family; every application now connects with the single owner credential, and an "and nothing more" assertion about an owner is vacuous, so the sections making it were removed rather than softened into checks that always pass. `tests/test_health_readiness.py` asserts the retired fragments are *absent* from the statement so they cannot drift back in. See `docs/reports/migration-decision-packet-2026-08-08.md` § Resolution.

`/health` is process liveness. `/ready` is profile-specific rollout evidence, and it now reports exactly five checks: `database_profile`, `receiver_identity`, `extensions`, `migration`, `serving_surface`. The `receiver_writer` profile mounts only the two authenticated receivers and requires a server-bound receiver actor. The `published_reader` profile mounts only `forecasts.py` and does not require receiver credentials. Both profiles require the exact Alembic revision and all four extensions. `combined_local` mounts the compatibility surface but always fails readiness. Redis is not a data-service dependency in phase one: publication commits an outbox record in the same PostgreSQL transaction, and another bounded dispatcher may deliver that event later.
