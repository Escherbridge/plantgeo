There is no `infra/cron-*` config, and therefore no Railway service, invoking any of:


## Access — getting a local reader on the production warehouse

Connection facts (not secret):

- host `switchback.proxy.rlwy.net`, port `37967`
- database `plantgeo`
- PostgreSQL 18 / PostGIS 3.6, `search_path=public`

Get the DSN yourself — it is not written down anywhere in this repo and must not be:

```bash
railway variables --service plantgeo-spatiotemporal-db --environment production --kv \
  | grep DATABASE_PUBLIC_URL
```

Notes for whoever analyses this data:

- Per the 2026-08-03 architecture decisions there are **no custom database
  roles**, so there is no separate read-only login to hand out. The DSN above is
  the superuser. Treat it accordingly; prefer `SET default_transaction_read_only
  = on;` at the top of an analysis session.
- Production writes are additive only. No destructive DDL, no truncating, no
  dropping, no service restarts.
- The Railway project `Aevani` is **shared with an unrelated application**
  (`aevani-web`, `Aevani-Postgress`, bucket `aevani-images`). Never bulk-reset
  anything at project scope.
- Day bucketing: use `substring(iso_text, 1, 10)::date`, never
  `(ts AT TIME ZONE 'UTC')::date`. 37.5% of USGS gauge readings carry `-07:00`,
  so the naive cast silently shifts them a day.

## Follow-ups

The gap above. Before adding services, decide whether these belong as nine more
Railway cron services or as one scheduled orchestrator that runs the
`forecast-*` sequence in dependency order. They are ordered work
(`run-iteration` → `reconcile-actuals` → `evaluate`), which nine independent
crons model badly. Recommend the orchestrator.

Blocked-by: nothing. This is the single highest-value item outstanding.

### 2. Redefine the NDVI forecast target as a 21-day composite

Hours of work. Measured: forecast skill +3.2% → +11.8%. The current daily target
sits at the observation-noise floor — noise SD 0.0499 against error SD 0.0456,
meaning the model is being scored mostly on noise it cannot predict.

### 3. Promote the 1,030 USDM polygons into `agri.drought_polygon_snapshot`

That table has **0 rows**, and 0 of 1,568 NDVI cells have any `signal_observation`
row. This is the actual ML blocker: the feature layer is empty, so no amount of

## Things that will mislead you

- **`models/` is SQLAlchemy ORM, not ML models.** 3,434 lines, zero runtime
  `.execute(`. The name is a trap for anyone restructuring this package.
- **`infra/cron-ingest/Dockerfile` deliberately omits `alembic/` and
  `alembic.ini`** so the container cannot run a migration by construction. Any
  new import edge that pulls migration machinery into an `ingest-*` import path
  breaks all nine cron services at runtime — and the test suite **cannot see
  it**, because tests run in a full checkout where those files exist. Only a
  container smoke test catches it. That Dockerfile's own comment cites
  `_alembic_config()` at "cli.py:266-267"; it is at `cli.py:313`. The line-pinned
  cross-file comments in this repo have already rotted.
- **Martin enumerates PostGIS tile functions only at process start.** One
  missing function 404s an entire comma-joined composite and hides *every*
  layer. Nothing in the pipeline restarts Martin after a tile migration.
- **A hidden browser tab suspends `requestAnimationFrame`**, so MapLibre never
  loads its style and the map renders blank. This looks exactly like a total
  layer outage and cost real time this session before being identified as an
  artefact of the automation tab, not a product bug.
- **postgres-js binds every JS number as OID 0.** A fractional parameter next to
  a bigint resolves as bigint and 500s. Cast it `::numeric`.
- **Only `vegetation` has multi-year depth.** The date slider correctly empties
  most layers before 2026-08-02. That is data history, not a slider bug.
