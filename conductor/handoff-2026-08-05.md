### Sizing — decided 2026-08-05: all three layers

`agri.signal_observation` grew **34 MB → 83 MB for 70,176 rows** — about
732 bytes/row. The reviewer decomposed this and confirmed it is arithmetically
right for the schema, not an anomaly: roughly half is indexes, dominated by
`uq_signal_observation_release_cell_signal_time`, which carries `signal_name`,
`source_parameter` and `support_key` as full varchars in every index tuple.
Making that cheaper means normalizing three columns into a lookup table — a real
migration touching every lane. Not worth it.

**Owner decision: all three layers.** 6,877,248 rows, ~5.0 GB against a 5,178 MB
database (~4.3 GB after the `metadata_json` fix below). Layer-1-only was offered
at ~1.64 GB and declined.

One cheap win taken instead: `metadata_json` was storing `source_parameter` — a
first-class column on the same row, the identical string — and
`native_grid_name`, already recorded in three other places. ~104 bytes inline,
never TOAST-compressed, **~690 MB of the projection storing nothing new**.

### Throughput — this task is NOT compute bound

Recorded because it will otherwise be re-proposed. Measured: 16 cells × 3
variables × 4 years = **21 s fetch, 98 s persist**. Persist is ~5× the fetch and
is database round-trips over the public proxy. The fetch is `asyncio` against
HTTP, already concurrent, and bounded by Open-Meteo's free-tier **daily quota**,
which is weighted by `locations × variables × timesteps` — chunk size changes
the request count but not the quota cost.

A rewrite in a faster language (Go was proposed) moves neither queue. The levers
that do, in order:

1. **A paid Open-Meteo key.** The quota wall is the entire ~98-day crawl. Remove
   it and the job is persist-bound — hours, not months.
2. **Run persist from an in-network Railway sandbox.** Measured 8–20× on the
   soil-survey backfill, which was round-trip bound for the same reason.
3. **`COPY` instead of per-row `INSERT`** on the persist path. The one real
   code-side win, and it is in Python where the lane already lives.

Concurrency above 4 is counterproductive while the quota holds; it only reaches
the wall sooner.

### A bug worth remembering

The rate-limit classifier originally matched bare nouns. Open-Meteo's daily wall
says `"Daily API request limit exceeded. Please try again tomorrow."` — which
contains no substring `"day"`. So a quota refusal classified as `unknown` and
slept 3×120 s per chunk, hanging a 32-chunk run for ~50 minutes doing nothing.
It now matches the provider's *adjectives* (`daily|day`, `hourly|hour`,
`minutely|minute`), with a regression test pinning the three exact live 429
bodies. Hour and day are never retried: sleeping through a quota wall turns a
refusal into an unexplained hang.

## Access — getting a local reader on the production warehouse

Connection facts (not secret):

- host `switchback.proxy.rlwy.net`, port `37967`
- database `plantgeo`
- PostgreSQL 18 / PostGIS 3.6, `search_path=public`

Get the DSN yourself — it is not written down anywhere in this repo and must not be:

```bash
railway variables --service plantgeo-spatiotemporal-db --environment production --kv \
  | grep DATABASE_PUBLIC_URL
```

Notes for whoever analyses this data:

- Per the 2026-08-03 architecture decisions there are **no custom database
  roles**, so there is no separate read-only login to hand out. The DSN above is
  the superuser. Treat it accordingly; prefer `SET default_transaction_read_only
  = on;` at the top of an analysis session.
- Production writes are additive only. No destructive DDL, no truncating, no
  dropping, no service restarts.
- The Railway project `Aevani` is **shared with an unrelated application**
  (`aevani-web`, `Aevani-Postgress`, bucket `aevani-images`). Never bulk-reset
  anything at project scope.
- Day bucketing: use `substring(iso_text, 1, 10)::date`, never
  `(ts AT TIME ZONE 'UTC')::date`. 37.5% of USGS gauge readings carry `-07:00`,
  so the naive cast silently shifts them a day.

## Follow-ups

Ordered by value per unit of effort.

### 1. Schedule the forecast and ML lanes — nothing does

The gap above. Before adding services, decide whether these belong as nine more
Railway cron services or as one scheduled orchestrator that runs the
`forecast-*` sequence in dependency order. They are ordered work
(`run-iteration` → `reconcile-actuals` → `evaluate`), which nine independent
crons model badly. Recommend the orchestrator.

Blocked-by: nothing. This is the single highest-value item outstanding.

### 2. Redefine the NDVI forecast target as a 21-day composite

Hours of work. Measured: forecast skill +3.2% → +11.8%. The current daily target
sits at the observation-noise floor — noise SD 0.0499 against error SD 0.0456,
meaning the model is being scored mostly on noise it cannot predict.

### 3. Promote the 1,030 USDM polygons into `agri.drought_polygon_snapshot`

That table has **0 rows**, and 0 of 1,568 NDVI cells have any `signal_observation`
row. This is the actual ML blocker: the feature layer is empty, so no amount of
model work helps. The polygons already exist ingested; they have never been
promoted into the plane the features read from.

### 4. `agri.covariate_feature_schema` is pinned to an immutable version

**A third ML blocker, distinct from the two above.** The schema pins its signal
list to the immutable `agri_covariates_v1`, so *any newly ingested signal is
invisible to training* until a new schema version is authored. The Open-Meteo
soil-moisture rows that just landed are already in this position: correct,
verified, in the warehouse, and unusable by the model.

This means ingesting more data does not, on its own, improve anything. Authoring
the next schema version is the step that converts ingestion into ML capability,
and it is a separate reviewed change. Sequence it before any further backfill
that exists to serve the model.

### 5. `ck_forecast_run_method` admits only `sql_linear|ml`

So the Monte Carlo forecast **cannot reach the serving contract** — there is no
value it is allowed to write. Either widen the constraint or decide MC is an
offline-only method. Currently it silently has nowhere to go.

### 6. Finish the soil-survey backfill

5,241 cells remain. `npm run backfill:soil-survey -- 5241`, from an in-network
sandbox — not a laptop, see the throughput note above.

### 7. FIRMS ranges never requested

`2022-10-05..2023-01-09` (97 days) and `2023-01-15..2026-08-01` (1,295 days).
Note the day-range clamp is 5, not 10 — measured against the live API, which
answers `400 Invalid day range. Expects [1..5].` for 6, 7 and 10.

### 8. No statement timeout on `local_source_loader_session` callers

`conductor/code_styleguides/python.md` requires a 120 s transaction-local
statement timeout on direct SQL callers. `forecast_iteration_session` callers
(`cli.py:590`, `cli.py:709`) and `vegetation_ndvi_plane.py:61` comply; **no
`local_source_loader_session` caller does.** Pre-existing across every lane, so
it is not one author's regression — but the Open-Meteo lane has by far the
largest transaction (219,300 rows plus a ~1 MB inline artifact per 50-cell
chunk) and holds an advisory xact lock while running against production over the
public proxy. Fix across all lanes in one pass.

### 9. Daily means are stored with a zero-width validity window

`historical_writer.py:1139-1140` writes `valid_from == valid_to == observed_at`
(midnight UTC). A 24-hour mean is valid over `[00:00, 24:00)`, not at an instant,
so a consumer doing interval logic on the contract view gets an empty interval.
The NASA and CDS lanes do the same (`:1363-1364`, `:1446-1447`), so this is a
**cross-lane convention question, not a regression** — but settle it before
6.8M more rows adopt it.

### 10. `metadata_json` waste exists in the NASA and CDS lanes too

The Open-Meteo lane's fix (above) leaves a per-lane divergence: NASA at
`historical_writer.py:1363-1364` and CDS at `:1446-1447` still duplicate a
first-class column into jsonb on every row. Either follow suit or accept that
the three lanes now persist different shapes.

### 11. `alembic upgrade head` silently targets PRODUCTION

**Highest-severity item in this list.** `alembic/env.py:14` sets its target from
`settings.database_url_sync` — the **`DATABASE_URL_SYNC`** variable — and `.env`
points that at `switchback.proxy.rlwy.net`. Overriding `DATABASE_URL` does
nothing; they are separate settings.

Found 2026-08-05 when a disposable test database was set up, `DATABASE_URL` was
exported to the throwaway container, and `alembic upgrade head` was run. **It
connected to production.** It applied zero migrations only because production
was already at head (`20260803_0018`). Had production been behind, it would have
migrated it silently.

`env.py` has no fail-closed guard: nothing prints the resolved host and nothing
refuses a production-looking DSN. Harden it — print the target host, and refuse
a `*.proxy.rlwy.net` DSN unless an explicit opt-in flag is set. Until then,
treat every local `alembic` command in this service as production-touching, and
override `DATABASE_URL_SYNC` rather than `DATABASE_URL`.

### 12. Open-Meteo attribution is missing, and CC-BY requires it

The app calls the Open-Meteo forecast API from
`src/lib/server/services/weather.ts:17` and renders **no attribution anywhere**.
CC-BY 4.0 requires this string where the data appears:

```html
<a href="https://open-meteo.com/">Weather data by Open-Meteo.com</a>
```

The UI already has attribution scaffolding in `SoilLayer.tsx` and
`VegetationLayer.tsx` — there is simply no entry for this source. Must be fixed
before the repo is published. Note a paid commercial licence removes the
**non-commercial** restriction but does **not** discharge attribution for the
underlying **Copernicus / ERA5-Land** data, which is a separate obligation.

## Things that will mislead you

- **`models/` is SQLAlchemy ORM, not ML models.** 3,434 lines, zero runtime
  `.execute(`. The name is a trap for anyone restructuring this package.
- **`infra/cron-ingest/Dockerfile` deliberately omits `alembic/` and
  `alembic.ini`** so the container cannot run a migration by construction. Any
  new import edge that pulls migration machinery into an `ingest-*` import path
  breaks all nine cron services at runtime — and the test suite **cannot see
  it**, because tests run in a full checkout where those files exist. Only a
  container smoke test catches it. That Dockerfile's own comment cites
  `_alembic_config()` at "cli.py:266-267"; it is at `cli.py:313`. The line-pinned
  cross-file comments in this repo have already rotted.
- **Martin enumerates PostGIS tile functions only at process start.** One
  missing function 404s an entire comma-joined composite and hides *every*
  layer. Nothing in the pipeline restarts Martin after a tile migration.
- **A hidden browser tab suspends `requestAnimationFrame`**, so MapLibre never
  loads its style and the map renders blank. This looks exactly like a total
  layer outage and cost real time this session before being identified as an
  artefact of the automation tab, not a product bug.
- **postgres-js binds every JS number as OID 0.** A fractional parameter next to
  a bigint resolves as bigint and 500s. Cast it `::numeric`.
- **Only `vegetation` has multi-year depth.** The date slider correctly empties
  most layers before 2026-08-02. That is data history, not a slider bug.
